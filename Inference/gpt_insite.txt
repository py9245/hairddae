좋아.
네 조건을 딱 맞춰서 정리하면 기준은 이거야.

* **속도는 최대한 올린다**
* **현재 선택 로직 / 합성 결과 / 픽셀 결과는 그대로 유지한다**
* **병렬화는 하되, 결과가 바뀌는 병렬화는 분리해서 다룬다**

이 조건이면, 지금 제일 먼저 건드릴 곳은 **tracking/segmentation이 아니라 attenuation + legacy overlay + postprocess**다. `prepare_runtime_frame()`는 이미 tracking과 segmentation을 `prepare_executor`로 병렬 실행하고 있고, 반대로 `HairOverlayRuntime.process_frame()`은 smoothing → user parsing → selection → compose → postprocess를 큰 락 안에서 길게 잡고 있으며, postprocess는 매 프레임 `connectedComponents`와 full-frame 좌표장 생성까지 다시 하고 있다. 또 user mask 쪽은 이미 reuse/hold 로직이 상당히 들어가 있으니, 그 임계값을 바꿔서 속도를 얻는 방식은 “결과 동일” 조건에 맞지 않는다.    

## 먼저 결론부터

**우선순위는 이렇게 가면 된다.**

1. `run_hair_overlay_poc.py`의 **legacy overlay 경로에서 static asset GPU upload / mask stack 생성 / crop slice 재준비를 캐시**
2. `overlay_postprocess_pipeline.py`의 **external background mask / full-frame grid / local background field 계산 재사용**
3. `hair_attenuation.py`의 **불필요한 copy / cvtColor / temp allocation 지연 및 재사용**
4. `hairddae_runtime.py`의 **global current-session + global lock 구조를 thread-local session context + per-session lock으로 바꾸기**
5. 그 다음에만 **transition frame / multi-asset blend branch 병렬화**
6. `rtc.py`의 `frame_age` 문제는 **별도 브랜치**로 처리. 이건 UX latency는 좋아지지만 “같은 프레임 시퀀스”는 바뀔 수 있다.

## 1) 제일 먼저: legacy overlay에서 정적 asset을 매 프레임 다시 올리지 않기

### 왜 여기가 1순위냐

지금 병목 수치상 `hair_overlay`가 크고, 네 경로 설명상 실제 합성 핵심은 `run_hair_overlay_poc.py`다. 이 파일은 asset bundle을 캐시로 읽어오긴 하지만, 실제 legacy overlay 단계에서는 **crop된 RGB / alpha / hair mask / face/protect mask stack을 매 프레임 다시 준비하고 GPU upload 후 warp**하는 구조다. 이건 “수학”이 아니라 **준비 비용**이라서, 캐시만 잘 잡으면 결과는 안 바뀌고 속도만 줄일 수 있는 대표 구간이다. `load_asset_bundle()`도 이미 LRU 캐시 구조를 갖고 있다. 

### 어디를 바꾸냐

* `run_hair_overlay_poc.py`

  * `load_asset_bundle()` 근처
  * `build_legacy_overlay_layer()` 근처
  * 필요하면 module-level cache 추가

### 어떻게 바꾸냐

핵심은 **정적인 asset 쪽 준비를 1회화**하는 거다.

지금 매 프레임 반복되는 것:

* `src_rgb = asset_image[src_y0:src_y1, src_x0:src_x1]`
* `src_alpha = ...`
* `src_hair = ...`
* `src_face`, `src_protect_face`
* `src_mask_stack = np.dstack([src_face, src_protect_face])`
* `opencv_cuda_upload(...)` 4회

이걸 아래처럼 바꿔.

#### A. CPU-side crop cache

asset bundle이 로드될 때, legacy 경로에서 쓸 crop를 미리 만들어 둬.

* `legacy_src_rgb`
* `legacy_src_alpha`
* `legacy_src_hair`
* `legacy_src_face`
* `legacy_src_protect_face`
* `legacy_src_mask_stack`

이 값들은 asset pose/metadata가 같으면 **프레임마다 절대 바뀌지 않음**.

#### B. GPU-side upload cache

그 다음 첫 사용 시에만 GPU로 올리고, 이후엔 재사용.

예시 구조:

```python
# module-level
_LEGACY_GPU_CACHE: dict[tuple[str, str], LegacyGpuCacheEntry] = {}
_LEGACY_GPU_CACHE_LOCK = threading.Lock()

@dataclass
class LegacyGpuCacheEntry:
    gpu_src_rgb: Any
    gpu_src_alpha: Any
    gpu_src_hair: Any
    gpu_src_mask_stack: Any
```

key는 최소한 아래가 들어가면 돼.

* `asset_root`
* `metadata_path` 또는 `asset_id`

`crop_box`가 asset마다 고정이면 key에 따로 안 넣어도 되고, 불안하면 포함.

#### C. warp만 프레임마다 수행

프레임마다 바뀌는 건 `matrix`, `roi_matrix`, `roi`뿐이다.
그래서 **warp는 계속 하되 source upload는 재사용**하면 된다.

### 결과 동일성은 왜 보장되냐

* source pixel 자체는 동일
* `warp_affine` 입력 동일
* interpolation / borderMode 동일
* alpha / skin suppression 수식 동일

즉 **같은 입력에 같은 warp만 적용**하니까 출력 픽셀은 같고, 준비 비용만 빠진다.

### 기대 효과

이건 네 현재 구조에서 가장 가능성 높은 **“큰 안전한 이득”**이다.
대체로 p50보다 **p95가 더 많이 줄 가능성**이 높다.
정확한 ms는 벤치가 필요하지만, 현재 CPU가 더 바쁘고 GPU 여유가 있다는 점을 보면, 이 준비/업로드 제거는 체감이 클 가능성이 높다.

### 주의점

OpenCV CUDA 객체를 여러 thread에서 동시에 쓰면 환경 따라 미묘할 수 있으니,
처음에는

* **cache는 넣되 render worker는 1개**
* 그 다음 안정성 확인 후 2개
  순서로 가는 게 안전하다.

## 2) 그 다음: overlay_postprocess의 “같은 계산 반복” 없애기

### 왜 여기가 2순위냐

`apply_overlay_postprocess()`는 결과 품질을 유지하는 마지막 단계라 절대 끄면 안 되는데,
코드를 보면 **같은 형태의 마스크/좌표 계산을 매 프레임 다시** 한다.

대표적으로:

* `_build_external_background_mask()`에서 `connectedComponents`
* `_build_local_background_field()` 안에서 다시 external background 계산
* `_build_directional_outer_ring_gate()`에서 full-frame `x_coords`, `y_coords` 생성
* `_backgroundize_mask()`에서 field를 ROI보다 넓은 폭으로 생성

이건 전부 **결과는 안 바꾸고 비용만 줄일 수 있는 구간**이다.    

### 어디를 바꾸냐

* `overlay_postprocess_pipeline.py`

  * `_build_external_background_mask`
  * `_build_local_background_field`
  * `_build_directional_outer_ring_gate`
  * `_build_outer_background_ring_mask`
  * `_backgroundize_mask`
  * `apply_overlay_postprocess`

### 어떻게 바꾸냐

#### A. external background mask를 한 번만 계산

지금은 `hair_binary_mask` 기준 external background를 여러 군데서 다시 만든다.

바꿀 형태:

* `apply_overlay_postprocess()`에서

  * `external_background_mask = _build_external_background_mask(hair_binary_mask)` 1회
* 그걸

  * `_build_outer_background_ring_mask(...)`
  * `_build_local_background_field(...)`
    로 넘겨

즉 시그니처를 이렇게 바꾸면 된다.

```python
def _build_local_background_field(..., external_background_mask: np.ndarray | None = None):
def _build_outer_background_ring_mask(..., external_background_mask: np.ndarray | None = None):
```

없으면 내부 계산, 있으면 재사용.

#### B. full-frame 좌표장 cache

`_build_directional_outer_ring_gate()`와 side fringe gate 쪽은 매번

```python
x_coords = np.broadcast_to(...)
y_coords = np.broadcast_to(...)
```

를 다시 만든다. shape가 288x512로 사실상 고정이면 이건 완전 낭비다.

```python
@lru_cache(maxsize=8)
def _coord_grids(height: int, width: int) -> tuple[np.ndarray, np.ndarray]:
    x = np.broadcast_to(np.arange(width, dtype=np.float32)[None, :], (height, width))
    y = np.broadcast_to(np.arange(height, dtype=np.float32)[:, None], (height, width))
    return x, y
```

그리고 두 함수에서 재사용.

이건 **출력 100% 동일**이다. 그냥 배열 생성만 캐시하는 거라서.

#### C. `_backgroundize_mask()`에서 ROI 폭만큼만 field 생성

지금 local background field가 있으면:

```python
field_by_col = np.tile(background_color[None, :], (output_frame_bgr.shape[1], 1))
field_by_col[field_cols] = field_colors
target_roi = field_by_col[x:x+width][None, :, :] * 0.97 + ...
```

이렇게 frame 전체 폭만큼 만들고 잘라 쓴다.

이걸 이렇게 바꿔.

* `field_cols_local = field_cols - x`
* `field_by_col = np.tile(background_color[None, :], (width, 1))`
* local range에만 assign

수학은 완전히 같고 메모리/할당만 줄어든다.

#### D. `_as_mask()` fast path

현재 shape 맞는 `uint8` binary mask도 다시 `np.where(mask > 0, 255, 0)`를 탄다.
hair/fringe/protect/coverage가 대부분 이미 binary라면 이 변환도 줄일 수 있다.

조심스럽게 fast path:

```python
if isinstance(mask, np.ndarray) and mask.shape == shape and mask.dtype == np.uint8:
    return mask
```

이건 upstream mask가 이미 binary라는 전제가 필요하니까,
처음엔 hair/fringe/protect처럼 **우리 파이프라인이 만든 마스크에만 적용**하는 게 안전하다.

### 기대 효과

여긴 큰 한 방보다는 **지속적 p50/p95 절감** 구간이다.
특히 postprocess가 every-frame라서 tail latency 줄이는 데 의미가 있다.

## 3) attenuation은 알고리즘 말고 “할당/복사/시점”만 줄여라

### 왜 이렇게 해야 하냐

attenuation은 지금 p50 39.8ms니까 절대 작은 구간이 아닌데,
여기서 threshold, work dimension, blur scale, suppression rule 같은 걸 바꾸면 **바로 결과가 바뀐다**.

그래서 여기서는 **연산식은 건드리지 말고**,
“언제 복사하느냐 / 어떤 임시 배열을 재사용하느냐 / 미리 해도 되는 계산을 미루느냐”만 만져야 한다. `apply_with_metadata()`는 내부 detail timing도 이미 남길 수 있게 되어 있다. 

### 어디를 바꾸냐

* `hair_attenuation.py`

  * `apply_with_metadata()` 중심

### 바로 할 수 있는 것

#### A. `output = frame_bgr.copy()`를 늦춰라

지금은 ROI가 잡히자마자 `output = frame_bgr.copy()`를 만든다.
그런데 그 뒤에

* alpha max가 너무 작아서 return
* mask invalid
  같은 early return이 있다.

즉 **복사해놓고 바로 버리는 프레임이 생긴다**.

가장 안전한 방식:

* `output = frame_bgr.copy()`를

  * 실제로 `roi` writeback 시작 직전
  * 혹은 `alpha_work.max() > 0.01` 확인 이후
    로 옮겨라.

#### B. `tone_source_gray`도 필요할 때만 만들어라

현재 grayscale 생성은 ROI setup 직후인데, 실제 사용은 tone metadata 경로다.
즉 alpha가 거의 0이면 이것도 헛일일 수 있다.

그래서

* `confidence_mask is not None`
* `alpha_work.max() > 0.01`
  확인 이후에 생성하도록 미뤄라.

이건 완전히 안전한 최적화다.

#### C. temp workspace 재사용

288x512 / max_work_dimension 176이면 work ROI shape 종류가 아주 많지 않다.
그래서 `HairAttenuator` 인스턴스 안에 작은 workspace cache를 둬서

* float alpha 버퍼
* uint8 binary 버퍼
* temporary blended ROI 버퍼
* `field_by_col`
  같은 걸 shape별로 재사용하면 Python allocation churn이 줄어든다.

중요한 점은:

* **배열 내용을 매번 덮어써야 하고**
* **shape별로 분리해야 하며**
* **thread-safe하게 써야 한다**

지금 구조상 attenuator는 세션당 별도 인스턴스가 아니면 lock이나 thread-local workspace가 필요하다.

#### D. `astype` 왕복 최소화

이 함수는 `float32 → uint8 → float32` 왕복이 꽤 많다.
가능한 한

* 계산 중에는 `float32`
* 마지막 writeback에서만 `uint8`
  로 정리해라.

이건 숫자식 자체는 그대로 두고 conversion 횟수만 줄이는 거라 안전하다.

#### E. detail_ms를 먼저 보고 세부 우선순위 정해라

여긴 이미

* `mask_prepare_ms`
* `mask_build_ms`
* `roi_setup_ms`
* `base_blur_ms`
* `color_estimation_ms`
* `lower_hairline_blend_ms`
* `eye_restore_ms`
* `total_ms`
  같은 detail을 내보낼 수 있다.

그러니까 먼저 최근 5분 p50/p95를 stage별로 뽑고,

* `base_blur_ms`가 크면 allocation/ROI reuse 쪽
* `color_estimation_ms`가 크면 analysis plane / 색 추정 재사용 쪽
* `lower_hairline_blend_ms`가 크면 crop-space temp buffer reuse 쪽
  으로 가면 된다.

### 여기서 건드리면 안 되는 것

* `segmentation_confidence_threshold`
* `strength`
* `blur_kernel_scale`
* `max_work_dimension`
* fringe/covered/outer suppression flags
* preserve eyes flag

이건 전부 **결과가 바뀐다**.

## 4) 아주 중요: `HairOverlayRuntime`는 지금 “global session pointer + global lock” 구조라서, 병렬화 전에 이걸 먼저 고쳐야 함

### 왜 중요하냐

겉으로는 session state가 따로 있는 것처럼 보이는데, 실제 구현은

* `self._current_session`
* `_require_session()`
* 각종 property (`_smoothed_user_row`, `_blend_assets`, `_transition` 등)
  로 **현재 session을 전역 포인터처럼 참조**한다.

그리고 `process_frame()` 전체가 `with self._lock:`으로 감싸져 있다.
이 뜻은:

* 다른 세션이 와도 전부 직렬화
* 그리고 지금 상태로는 session별 병렬화를 하려고 해도 `_current_session` 때문에 thread-safe하지 않다.   

### 여기서 안전하게 바꾸는 방법

**global current-session을 thread-local로 바꾸고, global lock을 per-session lock으로 축소**하는 게 정석이다.

#### A. `RuntimeSessionState`에 lock 추가

```python
@dataclass
class RuntimeSessionState:
    ...
    lock: threading.Lock = field(default_factory=threading.Lock, repr=False)
```

#### B. `_current_session`를 thread-local context로 변경

지금처럼 instance field 하나로 두면 두 thread가 동시에 다른 session을 처리할 때 깨진다.

예시:

```python
self._session_context = threading.local()

def _require_session(self) -> RuntimeSessionState:
    session = getattr(self._session_context, "current", None)
    if session is None:
        raise RuntimeError("Runtime session context is not initialized")
    return session
```

`process_frame()`에서:

```python
previous_session = getattr(self._session_context, "current", None)
self._session_context.current = session
try:
    ...
finally:
    self._session_context.current = previous_session
```

#### C. global lock 역할 줄이기

`self._lock`는 아래에만 써.

* `_get_or_create_session`
* `_ensure_landmarker`
* asset reload / global cache mutation

그리고 실제 frame 처리 본문은:

```python
with session.lock:
    ...
```

이렇게.

### 왜 이게 “결과 동일”에 맞냐

같은 session 안에서는 여전히 **순서와 상태 업데이트가 그대로**다.
다만 다른 session이 들어와도 서로 안 막히는 것뿐이다.

즉

* single-session 결과 동일
* multi-session에서도 각 session 내부 결과 동일
* throughput만 올라감

### 주의점

더 공격적으로 하려면 session lock 안에서도 pure compute를 밖으로 뺄 수 있지만,
그건 wall-clock 타이밍이 바뀌면서 `_transition` step 반영 시점이 달라질 수 있어서
지금 단계에선 권하지 않는다.

## 5) 병렬화는 여기서만 해라: “독립 branch”만

tracking/segmentation은 이미 병렬이다.
추가 병렬화는 **의존성이 없는 branch**에만 넣어야 결과가 안 바뀐다. 

### A. transition의 from/to frame 동시 계산

`compose_overlay_transition_frames()`는 from frame과 to frame을 각각 만든 뒤 마지막에 섞는다.
이 둘은 **서로 독립**이다.

그래서

* worker 2개로 `from_frame`, `to_frame` 동시 계산
* 둘 다 끝난 뒤 기존과 같은 `addWeighted`로 blend

이건 안전하다. `hairddae_runtime.py`의 overlay transition 경로도 동일한 패턴이고, bundle transition 쪽도 같은 아이디어를 쓸 수 있다.   

### B. multi-asset delta path 병렬화

`compose_overlay_blend_frame()`의 multi-asset 경로는 각 asset별 `compose_overlay_frame()` 결과를 만든 뒤, 마지막에 weighted delta를 누적한다.

이것도

* 각 asset overlay는 독립 계산
* 마지막 누적만 순서 보존
  이면 결과 유지가 가능하다.

중요:

* **future 완료 순서대로 더하면 안 됨**
* 반드시 **원래 asset 순서대로**
  `delta += (overlay_frame - base) * normalized_weight`
  해야 한다

그래야 float accumulation 순서까지 동일해서 1 LSB drift도 막을 수 있다.

### 다만 기대치를 현실적으로 말하면

이건 항상 이득이 큰 건 아니다.
왜냐하면 `_build_blend_assets()`가 꽤 자주 1개 asset로 수렴시키고, transition도 switch 구간에서만 생기기 때문이다.
그래서 이 병렬화는 **평상시 p50보다는 switch/transition 순간의 p95 개선** 쪽이다.  

---

## 6) 지금 당장 하지 말아야 할 것들

이건 빨라질 수는 있어도 **결과가 바뀐다**.

* `INFERENCE_RTC_PROCESS_MAX_DIMENSION / MIN_DIMENSION` 변경
* `INFERENCE_RTC_HAIR_ATTENUATION_MAX_WORK_DIMENSION` 변경
* renderer 바꾸기
* bundle_render on/off 바꾸기
* attenuation threshold / blur / strength 조정
* user parsing reuse threshold 조정
* face tracker / segmenter delegate 바꾸기
* fringe / outer bulk / covered suppression flag 변경

설정값들은 `Settings`에서 그대로 runtime behavior를 바꾼다. 이건 이번 요구사항에선 금지라고 보는 게 맞다. 

---

## 7) `frame_age`는 계산 병목 말고 스케줄링 문제일 가능성이 큼 — 하지만 이건 별도 브랜치

네가 준 수치에서 `queue_depth_max=0`인데 `frame_age`가 크다는 건,
“큐 적체”보다는 **프레임을 언제 집어오느냐** 쪽일 가능성이 높다.

내가 본 `rtc.py` 흐름상 `recv()`는 먼저 output slot을 기다린 뒤, 그 다음 최신 프레임을 꺼낸다.
이 순서면 buffer가 안 쌓여도 프레임은 이미 도착한 상태로 대기하게 되고, 그게 `frame_age`로 보인다. `rtc_max_pending_frames`도 settings에 있다.  

이걸

* 최신 프레임을 먼저 꺼내고
* 그 다음 output pacing을 맞추거나
* pacing 직전에 freshest frame을 다시 선택
  하는 식으로 바꾸면 UX latency는 확실히 줄 수 있다.

그런데 이건 **같은 output tick에 어떤 input frame이 매칭되느냐가 바뀐다**.
즉 “시각 결과는 더 최신”이 되지만, **동일한 프레임 시퀀스 재생**은 아니다.

그래서 이건 **성능 브랜치가 아니라 latency 브랜치**로 따로 빼는 게 맞다.

## 적용 후 검증은 이렇게 해야 함

“결과 동일”이 핵심이니까 벤치보다 **회귀 검증**이 먼저다.

### 반드시 비교할 것

같은 입력 프레임 시퀀스로 old/new를 돌려서 아래를 비교:

* `selected_asset_id`
* `selected_pose_key`
* `selection_mode`
* `blend_asset_ids`
* `blend_weights`
* `transition_progress`
* `coverage_mask` checksum
* 최종 `output_frame_bgr` md5/sha1

### 기준

* 1~3차 최적화는 **프레임 픽셀까지 동일**해야 함
* 4차(`rtc.py`)는 픽셀식은 같아도 **같은 tick의 입력 프레임이 달라질 수 있음**

### 테스트 시나리오

* 정면 고정
* 좌우 고개 빠른 yaw turn
* 위아래 pitch 큰 변화
* no-face / outlier / multi-face
* asset switch 직전/직후
